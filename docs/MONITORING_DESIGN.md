# Azure Server Fleet Management & Observability

## 1. Monitoring Overview

The monitoring architecture provides centralized observability for the Windows Server and Ubuntu Server virtual machines in the development environment.

Azure Monitor Agent (AMA) collects configured telemetry. Data Collection Rules (DCRs) define the collection settings and send the data to a Log Analytics Workspace. Azure Monitor alert rules detect selected operational conditions.

## 2. Monitoring Components

| Component | Purpose |
|---|---|
| Azure Monitor | Monitoring and alerting platform |
| Log Analytics Workspace | Central destination for collected logs |
| Azure Monitor Agent (AMA) | Collects telemetry from the VMs |
| Windows DCR | Defines Windows performance-counter and event-log collection |
| Linux DCR | Defines Linux performance-counter and Syslog collection |
| DCR associations | Associate each operating-system DCR with its VM |
| CPU metric alert | Detects sustained high CPU utilization |
| Heartbeat log-to-metric and metric alert | Detects missing VM Heartbeat signals |

## 3. Log Analytics Workspace

The development environment provisions a dedicated Log Analytics Workspace.

| Property | Value |
|---|---|
| Region | Canada Central |
| Retention | 30 days |
| Name | Generated from project, environment, region code, and random suffix |

The workspace name is generated by Terraform and is not a fixed identifier.

## 4. Azure Monitor Agent

AMA extensions are provisioned on both VMs:

- `AzureMonitorWindowsAgent` for Windows.
- `AzureMonitorLinuxAgent` for Linux.

The VMs have System Assigned Managed Identities. The monitoring configuration uses AMA rather than the legacy Log Analytics agent.

## 5. Data Collection Rules

Separate DCRs are created for Windows and Linux. Both send their configured data to the Log Analytics Workspace.

### 5.1 Windows collection

The Windows DCR collects performance counters at a 60-second sampling frequency.

Configured counters:

- `\Processor Information(_Total)\% Processor Time`
- `\Memory\Available Bytes`
- `\Memory\% Committed Bytes In Use`
- `\LogicalDisk(_Total)\% Free Space`
- `\LogicalDisk(_Total)\Free Megabytes`

Windows event collection includes:

| Log | XPath level filter |
|---|---|
| System | Levels 1, 2, and 3 |
| Application | Levels 1, 2, and 3 |

The Security event log is not included in the current DCR configuration.

### 5.2 Linux collection

The Linux DCR collects performance counters at a 60-second sampling frequency.

Configured counter groups include:

- Processor utilization
- Available and used memory
- Logical disk free and used space
- System load averages (1, 5, and 15 minutes)
- System uptime

Syslog collection includes the following facilities:

- `auth`
- `authpriv`
- `cron`
- `daemon`
- `kern`
- `syslog`
- `user`

Configured Syslog levels include Debug, Info, Notice, Warning, Error, Critical, Alert, and Emergency.

### 5.3 DCR associations

The Azure Monitor module creates DCR associations for the VM objects supplied by the virtual-machine module. Windows VMs are associated with the Windows DCR; Linux VMs are associated with the Linux DCR.

## 6. Alerting Strategy

Two alert paths are implemented.

| Alert | Scope | Condition | Evaluation |
|---|---|---|---|
| High CPU | Resource Group scope, targeting VM metric resources | Percentage CPU average greater than 80% | 5-minute frequency, 15-minute window |
| Heartbeat missing | Log Analytics Workspace | Heartbeat metric count less than 5 | 1-minute frequency, 5-minute window |

Both alert rules use severity 2 and are enabled.

### 6.1 CPU alert

The CPU metric alert monitors `Percentage CPU` using `Average` aggregation. It triggers when the value is greater than 80% over the configured 15-minute evaluation window.

### 6.2 Heartbeat alert

Heartbeat records are converted into a metric using a scheduled query rule configured for log-to-metric conversion. The `Computer` dimension is used to distinguish the VM series.

The metric alert monitors the `Heartbeat` metric in the Log Analytics Workspace. It triggers when the count is below 5 over a five-minute window, evaluated every minute.

## 7. Alert Notifications

The current implementation creates and validates alert rules but does not configure email or SMS delivery through an Action Group. Notification delivery remains outside the current scope.

The absence of an Action Group does not prevent the alert rules from entering Fired and Resolved states.

## 8. Validation

The following functional tests were reported as completed:

- AMA telemetry was observed for both VMs.
- Windows and Linux DCR associations were created.
- CPU alert behavior was tested.
- Both VMs were stopped to test missing Heartbeat behavior.
- Heartbeat alert instances entered the Fired state.
- After the VMs were powered on again and telemetry resumed, the alert instances transitioned to Resolved.

These tests validate the tested alert behavior in the development environment; they do not establish a production service-level objective.

## 9. Security and Cost Considerations

- Log Analytics retention is configured for 30 days.
- DCRs limit collection to the selected performance counters and event sources.
- Windows Security events are not collected by the current configuration.
- Workspace access should follow least privilege.
- Ingestion volume and retention should be monitored to control cost.
- Monitoring resources are managed through Terraform.

## 10. Terraform Implementation

Monitoring resources are implemented in:

- `terraform/modules/log-analytics/`
- `terraform/modules/azure-monitor/`

The Log Analytics module creates the workspace. The Azure Monitor module creates the Windows and Linux DCRs, their associations, the CPU alert, the Heartbeat log-to-metric rule, and the Heartbeat metric alert.
