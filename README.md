# Azure Server Fleet Management & Observability

## Overview

Azure Server Fleet Management & Observability is a Terraform-based Azure Cloud Engineering project that provisions and operates a small Windows and Linux virtual machine fleet.

The development environment combines private workload networking, Azure Bastion for administrative access, Azure Monitor and Log Analytics for observability, and Azure Update Manager for periodic assessment and scheduled patch installation.

The project follows the Microsoft Azure Well-Architected Framework (WAF), with particular attention to security, cost optimization, operational excellence, reliability, and performance efficiency.

## Objectives

- Provision Azure infrastructure using reusable Terraform modules.
- Manage Windows Server and Linux virtual machines.
- Provide administrative access through Azure Bastion without public IP addresses on workload VMs.
- Collect operating-system telemetry through Azure Monitor Agent and Data Collection Rules.
- Monitor VM CPU utilization and Heartbeat availability through Azure Monitor alerts.
- Assess and install operating-system updates using Azure Update Manager.
- Apply Infrastructure as Code, Git-based engineering practices, and documented validation.
- Keep implementation status and architectural decisions transparent.

## Architecture

The current architecture includes:

- Azure Resource Group.
- Azure Virtual Network and workload subnet.
- Network Security Group associated with the workload subnet.
- Dedicated `AzureBastionSubnet`.
- Azure Bastion Basic and its dedicated public IP.
- Windows Server 2022 Datacenter VM.
- Ubuntu Server 22.04 LTS VM.
- System Assigned Managed Identities.
- Azure Monitor Agent extensions.
- Windows and Linux Data Collection Rules and associations.
- Log Analytics Workspace.
- CPU metric alert.
- Heartbeat log-to-metric conversion and metric alert.
- Azure Update Manager Maintenance Configuration.
- Dynamic-scope maintenance assignment based on `Env = DEV`.

Workload VMs do not receive public IP addresses. Administrative access is provided through Azure Bastion. Current VM access uses local credentials; Entra ID login extensions are deployed, but Entra ID is not the current interactive authentication method.

## Monitoring

The monitoring implementation includes:

- 30-day Log Analytics retention.
- Windows performance counters and System/Application event collection.
- Linux performance counters and Syslog collection.
- CPU alert for average utilization above 80% over a 15-minute window.
- Heartbeat alert based on a Heartbeat metric count below 5 over a five-minute window.

The CPU and Heartbeat alerts were functionally tested. The Heartbeat alert was observed entering Fired when the VMs were stopped and Resolved after they were restarted and telemetry resumed.

Email/SMS notifications through an Action Group are not currently implemented.

See [`docs/MONITORING_DESIGN.md`](docs/MONITORING_DESIGN.md).

## Update Management

Azure Update Manager is configured using the customer-managed `InGuestPatch` approach.

Current maintenance configuration:

| Setting | Value |
|---|---|
| Assessment | Periodic, platform-managed |
| Installation recurrence | Weekly |
| Day | Tuesday |
| Start time | 14:00 |
| Time zone | `Eastern Standard Time` (Québec local time) |
| Duration | 3 hours |
| Reboot behavior | `IfRequired` |
| Assignment | Dynamic scope using `Env = DEV` |

The schedule is externalized through Terraform variables. Periodic assessment is enabled on both VMs. The Maintenance Configuration and dynamic-scope assignment were deployed, and patch installation was executed and tested.

Azure Policy is not implemented; it remains a planned governance enhancement.

See [`docs/UPDATE_MANAGEMENT.md`](docs/UPDATE_MANAGEMENT.md).

## Engineering Principles

- Follow the Azure Well-Architected Framework.
- Use reusable Terraform modules with clear responsibilities.
- Keep environment-specific settings separate from reusable module logic.
- Protect credentials, private keys, state files, and sensitive plan output.
- Use private workload networking and least-privilege access.
- Validate Terraform changes before deployment.
- Review `terraform plan` before applying infrastructure changes.
- Test deployed behavior and record evidence.
- Keep architecture and implementation documentation aligned.
- Use Git branches and descriptive English commit messages.
- Distinguish implemented capabilities from planned improvements.
